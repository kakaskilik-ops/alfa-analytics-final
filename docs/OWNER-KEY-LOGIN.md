# Вход по личному ключу

На сайте форма «Ключ доступа» заменяет письма и OTP. До подтверждения настоящей сессии владельца приложение и запросы его разделов не запускаются. Отсутствие настроек или ошибка проверки не открывают сайт. Сессия сохраняется в текущей вкладке до выхода/истечения; переходы и перезагрузка вкладки не требуют повторного ввода. После закрытия вкладки и нового посещения потребуется ключ.

## Настройка владельцем

В Supabase **только проекта vlfzjvwgrvyllvshwmzr** сохранить `OWNER_ACCESS_KEY` (24–256 символов) в Edge Function Secrets. Лучше случайный длинный ключ или длинная непредсказуемая фраза. Значение не передавать разработчику или в чат, не добавлять в VITE/GitHub/frontend. Разработчик проверяет лишь признак наличия и результат серверного теста, не читает секрет.

После выпуска открыть https://alfammetal.ru, ввести свой ключ и нажать «Войти». Почта и регистрация не нужны. «Выйти из личного кабинета» очищает сессию и закрывает разделы. При ошибке ключа показывается отказ; после превышения попыток — сообщение о 15 минутах.

Смена секрета меняет ключ для новых входов. Она не отзывает уже выданные Supabase Auth-сессии автоматически; при компрометации нужно также завершить существующие сессии через Supabase Auth/выход на устройствах. Ключ приложение не сохраняет в localStorage/sessionStorage; стандартные токены Auth-сессии Supabase SDK хранит только в sessionStorage текущей вкладки (при запрете хранилища — в памяти страницы). Вводимый ключ передаётся единожды по HTTPS, как пароль, а не в URL.

## Серверная проверка

`owner-key-login` сравнивает SHA-256 ключей с проходом по всем байтам, не возвращает секрет/хеш/почту/одноразовую ссылку. После правильного ключа берёт единственный ID из закрытого allowlist владельца, проверяет существование и подтверждение аккаунта. Запрос не может выбрать email/user_id другого человека. Аккаунт с проверенным MFA не получает обхода второго фактора: такой вход отклоняется.

Через официальный Admin generateLink создаётся одноразовый токен (метод **не отправляет письмо**), который немедленно проверяется сервером через verifyOtp. В браузер возвращаются только access/refresh токены собственной Auth-сессии владельца. Service-role ключ остаётся серверным. Проверка RLS выполняется настоящим JWT; `has_smm_owner_access` не подменяется клиентским флагом.

Атомарные счётчики Postgres: 8 попыток на хеш сети / 15 минут и 200 общих / 15 минут. Сетевые заголовки — только вспомогательная справедливость; глобальная граница действует при смене/подделке IP. Сырой IP и ключ не пишутся в счётчики. Старые окна удаляются через сутки. Доступ к счётчикам и lookup владельца есть только у сервера; anonymous/authenticated не могут обнулить лимиты или назначить владельца. Есть honeypot, лимит тела 2 КБ, ограничения Origin, no-store и обезличенные ошибки.

## Реальный тест без раскрытия личного ключа

`verify-owner-login` — закрытая эксплуатационная проверка по существующему collector token. Она внутри Edge использует секрет с обычным `owner-key-login`, соблюдая его квоты, проверяет настоящий Auth getUser, совпадение владельца, owner RPC и SELECT защищённой SMM-таблицы. В `finally` отзывает **только тестовую сессию** через scope=local. Другие сессии и данные не меняются. Возвращает только четыре булевых результата, без ключа, JWT, UUID, email или строк SMM. Публичный вызов запрещён. Cron для этого теста не создаётся.

Это подтверждает настоящий серверный вход правильным ключом без чтения ключа разработчиком. Вход в личном браузере владелец выполняет сам. Тесты с фиктивным ключом/сессией выполняются исключительно на localhost/в изолированной БД.

## Границы защиты

Закрытый интерфейс и SMM-таблица доступны только подтверждённому владельцу; RLS SMM сохраняется. Существующие **общедоступные** API открытых ориентиров World Bank/новостей не превращаются этим экраном в секретные данные. Лицензированные SMM-данные в них не попадают. Старый серверный анонимный ИИ сохраняет свои proof, кеш и квоты; сам Groq и его бюджет этот релиз не меняет.

## Проверки и выпуск

18.11.2026 выполнена настоящая защищённая проверка в `vlfzjvwgrvyllvshwmzr`: HTTP 200, `correctKeyLogin=true`, `realAuthSession=true`, `ownerRlsAccess=true`, `testSessionRevoked=true`. Ключ читался только внутри Edge, значение/токены не возвращались разработчику. Внешний неверный ключ получил 401; анонимные обращения к эксплуатационному тесту, owner lookup, счётчикам и приватной SMM-таблице получили 401. Production-лимит до исчерпания не доводился; его границы/конкурентность проверены в изолированном Postgres.

Новых предупреждений Security Advisor относительно предыдущего выпуска нет. Сохранены прежние: намеренная [узкая SECURITY DEFINER-проверка собственного доступа](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable) и выключенная [проверка утёкших паролей Auth](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). Настройки Auth/тарифов не менялись; новый ключ не передаётся сторонним сервисам проверки паролей.

Тестируются неверный ключ, квоты, отсутствие настройки, чужой Origin, honeypot, подмена владельца, MFA и ошибочный upstream, выдача сессии, отсутствие секрета в ответах/хранилищах. SQL проверяет атомарные границы и недоступность счётчиков/lookup браузеру. Браузер проверяет настоящую границу монтирования приложения, 13 материалов после входа, отказ/выход и мобильный экран. Перед выпуском сохранить предыдущую версию/метаданные без секретов, удержать frontend Deploy до новой миграции и развёртывания двух функций, выполнить защищённый реальный тест и отрицательный запрос, затем штатный Deploy и проверку домена. При провале реального теста frontend не публиковать.
